--------------------------------
KEY OBSERVATIONS
--------------------------------

1. At 1M records, full table scans became substantially slower,
   reaching 6–7.5 seconds for SMART attribute filters.

2. Secondary indexes reduced query latency to below 0.2 seconds for both
   benchmark queries.

3. Phoenix execution plans changed from full scans over SMART_TELEMETRY
   to range scans over secondary index tables.

4. Index creation overhead increased with dataset size, taking roughly
   17–18 seconds per index at 1M rows.

5. The read-performance benefit was substantial for repeated analytical
   queries, with observed speedups of ~97.4x and ~36.1x.

--------------------------------
CONCLUSION
--------------------------------

At 1M records, Apache Phoenix secondary indexing produced major query
performance improvements over HBase-backed SMART telemetry data. The results
show that Phoenix provides an effective SQL interface over HBase while enabling
index-based query optimization. The tradeoff is additional index build and
maintenance cost, but for repeated analytical workloads, the performance gains
are significant.
