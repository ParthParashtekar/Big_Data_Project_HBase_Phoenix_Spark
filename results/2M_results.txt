--------------------------------
SYSTEM BEHAVIOR
--------------------------------

During initial query execution, Phoenix reported:

ERROR 1108 (XCL08): Cache of region boundaries are out of date.

Resolution:
- Closed Phoenix connection using !closeall
- Reconnected using sqlline.py localhost
- Query succeeded after reconnect

Observation:
At 2M records, HBase region splitting caused Phoenix client metadata/cache
to become stale. Reconnecting refreshed region boundary metadata.

--------------------------------
KEY OBSERVATIONS
--------------------------------

1. At 2M records, full table scans required approximately 7–9 seconds.

2. Phoenix secondary indexing reduced query latency to under 0.25 seconds.

3. Execution plans changed from parallel full scans over SMART_TELEMETRY
   to range scans over Phoenix secondary index tables.

4. The no-index plan used 4 chunks, indicating that HBase had begun splitting
   data into multiple regions/chunks at larger scale.

5. Phoenix encountered stale region boundary cache behavior after scaling,
   which was resolved by reconnecting the client.

6. Index build overhead increased with scale, reaching approximately
   24–26 seconds per index.

--------------------------------
CONCLUSION
--------------------------------

At 2M records, Apache Phoenix secondary indexing continued to provide
substantial query performance gains over HBase-backed SMART telemetry data.
The experiment also exposed real distributed-system behavior, including region
boundary cache staleness after HBase region changes. Despite this, the system
remained recoverable and indexed query performance remained strong.
